# 納品場所マスタ・RFQ・freee連携

2026-10-15実装・本番反映済み。Phase 3の販売見積・RFQ改善として、既存PDF／OCR取込を拡張する。ユーザーがfreeeへの納品場所書込を確認し、既存機能の回帰確認後に完了としてクローズした。

## 操作

1. RFQ詳細上部の「納品場所」でプルダウンから選ぶか、場所を手入力して「納品場所を保存」を押す。登録・編集画面からも入力できる。
2. 新しい場所はRFQとマスタに同じトランザクションで保存され、他の案件でも候補に表示される。空欄は未指定。全角・半角、大文字・小文字、連続空白を正規化した同一名は既存候補を再利用する。
3. メニューの「納品場所」で一覧検索・登録・無効化・再有効化ができる。名称を訂正する場合は正しい候補を登録し、旧候補を無効化する。過去RFQ・見積の名称は変えない。
4. 販売見積の「納品場所（RFQから反映）」とプレビューを確認し、「販売見積を保存」で保存版に固定する。RFQを変更した後は再保存が必要。転記済みの見積を変更する場合は既存の改訂操作を使う。
5. freee転記確認にも納品場所を表示する。新規は`POST https://api.freee.co.jp/iv/quotations`の`delivery_location`へ選択名を設定する。既存の未提示見積を改訂する操作では、従来のGET照合＋同一IDのPUTを維持し、新しい納品場所を設定する。

## PDF／RFQ取込

- 画像・PDFのOCR、仕入先見積PDF、表貼付・CSV・Excel取込で、`納品場所`／`納品先`／`納入場所`／`納入先`／`お届け先`／`Delivery Location`／`Ship to`という明示ラベルや表の納品場所列を抽出する。
- 既存の有効マスタと正規化後に一意一致すれば自動選択する。未登録なら新規候補、複数なら選択欄を表示する。類似名・住所の推測一致は行わない。無効な候補は再有効化または別候補の選択を案内する。
- 抽出結果は利用者が確認して「納品場所を保存」を押して確定する。品目の取込とは独立した保存操作であり、品目だけを登録しても納品場所は保存されない。既存のRFQ納品場所を無断で上書きしない。
- OCRの表復元で表外のヘッダーが失われる場合にも、元の抽出文の納品場所を保持する。納品場所のヘッダーを品目として登録しない。
- 納品場所の抽出・照合に新しい課金APIは使わない。OCRの明示実行・ファイル上限は従来どおり。

## データ・保護

- `deliveryLocations/{sha256(normalizedName)}`：`name`、`normalizedName`、`active`、`archivedAt`、作成／更新日時と操作者。作成・更新は認証済みユーザーのみ。名称・作成情報は不変、物理削除は禁止する。
- `rfqs/{rfqId}`：任意の`deliveryLocationId`、`deliveryLocationName`を追加する。旧データの一括移行は不要。無効化した場所を保持する案件の通常編集は可能だが、新たな選択には使えない。
- `salesQuotes/{rfqId}/freeeExports/current`と`revisions/{revision}`の`preview.settings`にID・名称、`payload.delivery_location`に送信名を保存する。過去の保存版・転記結果は変更しない。
- 保存時にサーバーがRFQとマスタを再取得し、クライアントの選択・最新RFQとの一致を検証する。保存後にRFQの場所が変わった場合は送信開始前にも拒否する。
- freee応答の納品場所も一致検証に含める。違う場合は要確認とし、自動再作成しない。既存の重複送信防止、手修正保護、結果不明のロックを維持する。
- 上書き確認で指定した納品場所は、その場所だけを明示的な変更対象とする。GET結果の納品場所を前回記録値へ戻したハッシュ照合で、他の項目が前回と一致する場合のみPUTを許可する。旧保存版に場所の記録がない場合は空値のみを照合候補にし、未知の場所を推測しない。納品場所を指定していない更新では、freee側の場所の変更も従来どおり保護する。
- 「販売見積を保存」はIEPpurchaseへの保存であり、freee反映は確認画面での実行後に確定する。反映未完了の理由をボタン付近に示し、改訂中・失敗中も前回のfreee見積書リンクを表示する。成功時は転記済みとなり、同じ版の再試行ボタンは表示しない。
- 場所は改行・制御文字を含まない255文字以内。未指定の新規見積ではAPI項目を省略する。公式QuotationRequestの最小長が1のため、場所付き見積を同一IDで空欄へ改訂する操作は保存前に拒否し、場所の指定または新規改訂を案内する。
- 公式仕様：<https://github.com/freee/freee-api-schema/blob/master/iv/open-api-3/api-schema.yml> のQuotationRequest.delivery_location。

## 既存機能と費用の確認（2026-10-15）

- 変更はRFQ・見積・取込へ納品場所を通す追加、Rules、テスト、資料、Functionsの生成済みJSに分かれる。既存機能の全面書き換えはしていない。
- 旧RFQは場所未指定のまま読み書きできる。過去見積を自動更新せず、従来の金額計算、改訂、新規／同一ID更新、取引先照合、重複転記防止を維持する。納品場所を変えた場合だけ、新しい見積保存を要求する。
- 新規の課金API・AI判定・定期処理・自動OCR・自動freee転記・Secretを追加していない。納品場所の抽出と照合は、取得済みテキストに対する文字列処理で行う。OCRとfreeeへのHTTPリクエスト数はこの機能のためには増やしていない。
- 増分は候補一覧のFirestore読取、案件の納品場所保存、選択したマスタの検証読取、短い文字列の保存容量。既存場所の選択ではマスタを毎回更新せず、初回登録・有効／無効変更時だけマスタへ書く。画面を閉じたら購読を解除し、タイマーで全件再取得する処理はない。
- Firestoreは読取・書込・保存容量等に応じて課金されるため、候補数・画面利用回数・再接続等に比例した増加はある。2〜5名・月10〜100案件という想定では、この追加だけで大幅に費用が増える構造ではないと判断するが、プロジェクト全体の無料枠消費や実利用額は別に確認が必要。
- 4関数の反映前後を比較し、すべて`minInstances=0`、256MiB・1CPU、freee3関数は従来の最大20台・同時処理80・60秒、OCRは最大1台・同時処理2・90秒を維持している。実行アカウント・Ingress・Secret参照も一致。関数総数は14件で追加なし、対象外10関数の更新日時にも変更なし。記録: `tmp/delivery-location-preview/verified-comparison.json`。
- 公式料金資料：<https://firebase.google.com/docs/firestore/pricing>、<https://cloud.google.com/vision/pricing>。ここでは追加機能の構造を確認しており、実請求額が0円であるとの保証はしていない。
