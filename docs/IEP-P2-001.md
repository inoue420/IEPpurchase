## 4. データ設計（追加項目は案）

### 共通規約

- 内部IDはFirestore自動ID。案件番号・行番号・品番を参照キーにしない。
- rfqIdとrfqItemIdで追跡し、保存時に同一案件・参照先存在・有効状態を検証。
- Firestore Document型と入力型を分離。新機能の未指定参照/日付はnull、備考は空文字。既存RFQの空文字は境界で変換し、既存データを一括移行しない。
- 日付はTimestamp。業務日付は日本時間、期限は当日末まで有効。createdAt/updatedAt/selectedAtはサーバー時刻。retrievedAt（観測日時）は保存日時と区別。
- 可変レコードの共通項目: createdAt/createdBy/updatedAt/updatedBy、revision（初期1）、archivedAt/archivedBy（初期null）。物理削除なし。
- 見積/採用の改訂は旧revisionをrevisions/{revisionId}へ不変保存し、現行更新と原子的に処理。EC価格は上書きせず新IDで追加。
- マスター名変更/無効化後も、過去Snapshotの名称と価格は変えない。

### supplierQuoteRequests/{requestId}

正式資料は概要のみ。1依頼=1RFQ・1仕入先とする追加設計案。

| 項目 | 型・制約 |
| --- | --- |
| rfqId / supplierId | 必須ID |
| supplierName | 依頼時の名称Snapshot |
| rfqItemIds | 重複なし・1件以上。同一RFQの有効品目ID配列 |
| requestedAt / responseDueDate | Timestampまたはnull。依頼済みではrequestedAt必須。回答期限は依頼日以降 |
| status | draft / requested / partially_answered / answered / cancelled |
| note | 手動で記録する依頼方法・連絡内容、最大5000文字 |

状態: 下書き→依頼済み→一部回答→回答済み（依頼済み→回答済みも可）。未取消から取消可。状態訂正は理由付きで履歴を残す。
「依頼済み」は外部で実施した依頼の記録であり、保存でメールは送らない。
回答状態は手動記録。見積紐付け導入後は有効回答明細との整合を確認する。
回答見積はsupplierQuotes.requestIdを正規参照にする（1依頼:複数見積）。依頼側へ見積ID配列を重複保存しない。
P2-002は依頼CRUD・取消・再表示まで。回答見積の選択・検証はP2-003/004で接続する。

### supplierQuotes/{quoteId} と items/{quoteItemId}

| 保存先 | 正式項目 | 追加案 |
| --- | --- | --- |
| ヘッダー | supplierId, quoteNumber, quoteDate, validUntil, rfqId, documentId, subtotal, tax, total, createdAt | supplierName, requestId(nullable), currency=JPY, status(draft/valid/withdrawn), 共通変更項目、送料集計・税内訳 |
| 明細 | rfqItemId, productId, partNumber, quantity, unitPrice, shippingFee, deliveryDate | rfqId, itemName, unit, taxCategory, taxRateBps, shippingTaxCategory, shippingTaxRateBps, lineSubtotal/lineTax/lineTotal, stockStatus(nullable), itemUrl(nullable), note, 共通変更項目 |

documentIdは添付未利用時null、validUntil不明はnull。見積番号は外部番号で内部IDとは別。
関連明細作成後にrfqId/supplierId/requestIdを付け替えず、別見積を作る。明細は1RFQ品目を参照。
明細変更・合計・旧revisionを原子的に保存し、入力された合計を信頼せず再計算。
価格履歴保護はP2-003/004から実装し、P2-008まで上書き運用を許容しない。

### marketplaceOffers/{offerId}

正式項目: rfqId, rfqItemId, source(amazon/rakuten/other), externalItemId, sellerName, itemName, partNumber, quantity, unitPrice, shippingFee, totalPrice, stockStatus, estimatedDeliveryDate, itemUrl, retrievedAt。
追加案: productId(nullable), unit, currency=JPY, taxCategory, taxRateBps, shippingTaxCategory, shippingTaxRateBps, subtotal, tax, note, createdAt/createdBy, supersedesOfferId(nullable)。
送料不明はshippingFee/totalPriceをnullとする（正式型numberからの拡張案）。不明を0円にしない。
再取得・訂正は新ID追加。旧Snapshotは変更/削除不可。URLはhttp/httpsのみ、未取得はnull。
rawDataは手入力では保存せず、API導入時も必要な公開商品情報に限定する。

### sourcingDecisions/{decisionId}

正式項目: rfqId, rfqItemId, sourceType(supplier_quote/amazon/rakuten/manual), sourceRecordId, supplierId, supplierName, selectedQuantity, unitCost, shippingCost, totalCost, selectedBy, selectedAt, reason。
追加案: sourceQuoteId(nullable), sourceRevision, status(active/cancelled), currency, itemName, partNumber, unit, taxCategory, taxRateBps, subtotal/tax, sourceSnapshot, revision, createdAt/createdBy/updatedAt/updatedBy, cancelledAt/cancelledBy。

- 仕入先見積: sourceRecordId=quoteItemId、sourceQuoteId=quoteId。ヘッダーだけでなく明細を特定する。
- EC: sourceRecordId=offerId、sourceQuoteId=null。otherはsourceType=manualとし元sourceをSnapshotに保持。初期は候補なし直接採用を設けない。
- 採用時に名称・品番・単位・価格・税・数量・送料・有効期限・取得日時・元revisionを固定保存。元候補変更で原価を変えない。
- 1品目に複数active採用を許容。同一候補のactive採用重複は拒否し、数量変更は改訂とする。

## 5. 金額・送料・期限・数量（承認待ち案）

### 金額・税

- 初期JPY、金額は0以上の安全な整数円。taxCategory=exclusive（税抜）/inclusive（税込）/exempt（非課税）。税区分不明は参考表示、確定まで採用不可。
- 税率は基点の整数taxRateBps（例10%=1000）。税率を表示価格から推測しない。これは計算方式の提案であり税務判断ではない。
- 商品代と送料で別の税区分・税率を保存。各構成額で税抜Bの税はfloor(B*r/10000)、税込Gの内税はfloor(G*r/(10000+r))、非課税は0。
- 比較は税込送料込総額。元の税込/税抜単価も表示。subtotal=税抜相当額、tax=内税/外税合計、total=subtotal+tax。
- 明細の構成額ごとに端数切捨て後、ヘッダーへ集計。仕入先見積書の端数処理と違う場合は差額を表示し、黙って一致扱いにしない。税率別一括計算・調整額が必要ならP2-004前に確認。
- 例: 税抜1000円×2+税抜送料500円、双方10%ならsubtotal=2500、tax=250、total=2750。税込1100円×2+税込送料550円も総額2750。

### 送料・候補条件

- 見積全体の送料は明細へ手動配賦（例600円=400+200）。ヘッダー送料は集計表示のみで二重加算しない。
- 送料無料は0、未確認は不明。見積有効化/採用には送料の確定が必要。
- 一部数量の採用は送料を自動比例計算せず、採用数量での送料を確認して保存する。共通配送の調整は金額と理由を記録し、元候補と区別。
- 数量条件・単位が違う候補を同条件として順位付けしない。単位不一致は自動換算しない。
- 期限切れは明示し、理由付きで採用可能とする案。期限不明・在庫不明・納期不明も別表示し確認内容を理由へ残す。在庫なし、取消/撤回/アーカイブ済み、別案件の候補は採用不可。

### 数量・同時操作

- 既存RFQは小数数量を許容しているため整数限定へ変更しない。後続の演算は十進数として正確に扱い、円未満は構成額ごとに切捨てる。許容精度は実装前に明示し、既存値を黙って丸めない。
- active採用数量合計<=RFQ必要数。必要数10に6+4可、6+5不可。未採用残数を表示。採用数は候補提示数以下。
- P2-007では品目ごとの集計/ロック文書（案: rfqs/{rfqId}/sourcingStates/{rfqItemId}）を用意し、認可されたサーバートランザクションで採用・集計・履歴を更新。クライアント検証だけで超過を防いだことにしない。
- 採用/変更/解除とRFQ数量減少は同じロックを使用。採用中の品目取消/アーカイブ/単位変更は拒否し、先に採用解除。既存品目更新経路とRulesもP2-007で保護する。
- 同じ操作IDの再送は結果再利用、二重採用なし。取消は合計から除外するが履歴を保持。
- 採用・集計はクライアント直接書込禁止。サーバー側でactive/role、参照ID、金額、数量を再検証する。
- Cloud Functionsの導入・実行環境/費用条件はP2-007前に確認。本タスクで課金有効化しない。

## 6. 履歴・認可・クエリ・添付

- Firestoreのusers.active/role認可を継承。未認証・無効・未登録拒否。admin/memberは通常業務、users管理はadmin。未定義パス拒否。
- 各タスクで必須キー/型/上限/不変ID/親子整合/時刻を検証。重要な合計処理はサーバー検証またはRulesで整合を保証し、改ざん可能な合計を許可しない。
- auditLogsは正式仕様18に従いuserId/userName/action/entityType/entityId/rfqId/before/after/createdAtを保存。不変履歴の更新/削除は拒否。業務更新と原子的に記録し、履歴失敗なら更新も失敗。
- Phase 1 auditLogs基盤は未実装。P2-008までに不足の扱いと実装担当タスクを確定し、接続前提を満たす。
- クエリはRFQ起点。候補はrfqId+rfqItemId、依頼/見積はrfqId、回答見積はrequestId。明細は見積subcollection。全案件の候補を毎回読まない。
- Index候補: offers(rfqId,rfqItemId,retrievedAt)、requests(rfqId,requestedAt)、decisions(rfqId,rfqItemId,status,selectedAt)。実クエリを決定した各タスクでfirestore.indexes.jsonへ追加。
- documentsは正式仕様17（fileName/storagePath/mimeType/fileSize/documentType/entityType/entityId/rfqId/uploadedBy/createdAt）。documentType=supplier_quote、entityId=quoteId。
- ファイルパス案: rfqs/{rfqId}/{documentId}（既存Storage構造を維持）。元fileNameはメタデータに保持。
- 現Storageは認証有無のみ。P2-009でactive/role・RFQ/見積整合・形式/10MB上限を検証。アップロード後メタデータ失敗時の再試行/孤立ファイルも確認。
- 本番Storage条件未承認なら添付保留とし、総合完了判定で受入範囲を明示する。
